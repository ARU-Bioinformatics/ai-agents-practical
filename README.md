# AI agents for bioinformatics – a browser practical

**A two-hour practical on using AI assistants and AI agents for bioinformatics, and on making what they do reproducible.**

Students look at real sequencing data with their own commands, and then answer one question – which genotype does the sample NA12878 have at *CYP2C19\*2*? – with an AI **assistant** that writes commands for them, and with an AI **agent** that runs the commands itself, in four ways of working (approve each step, plan first, autonomous, write a script). Then they turn one of the agent's runs into an analysis that anyone can repeat: a record, a script, a test in a fresh folder, checksums, and a statement of what the AI did.

Everything runs in the student's browser. The programs are the real ones – **fastp, minimap2, Bowtie 2, samtools, bcftools, bedtools, seqtk, jq and the GNU text tools**, compiled to WebAssembly – and the AI is a **real model**: each student enters an API key (Google's Gemini API has a free tier; [Before the session](#before-the-session) says what to check before you rely on it). There is no simulated assistant and no canned output. Nothing is installed, and the site is static (HTML, CSS, JavaScript), so it can be hosted free on **GitHub Pages**.

## The practical

One page, `index.html`: the instructions on the left, a workbench on the right with three tabs – **Terminal**, **Files** (folders, an editor, a viewer for reports) and **AI** (Chat and Agent).

| Chapter | What students do | Time |
|---|---|---|
| 0 · Start here | The question (*CYP2C19\*2* and clopidogrel); assistant or agent – the loop of an agent; connect the AI with a key; three rules (no personal data in an AI tool, the result is yours, a key is a password) | 10 min |
| 1 · Look first | Before any AI: the files, the reads, checksums (`md5sum -c`), quality control with **fastp** and its report, the versions of the programs. You cannot judge an agent's work on data you have never looked at | 20 min |
| 2 · The assistant | Ask the Chat for the mapping and variant-calling commands, run them one by one, read the results; find the genotype (0/1) and its evidence; find the assistant's limits – it cannot see the files, and only knows that `bwa` is missing because the page told it | 20 min |
| 3 · The agent | The same task five times, in four ways. **Approve each step** (and change or refuse one); **Plan first** (ask for a change to the plan, then compare plan and record); **Autonomous**, twice (nothing makes the runs the same – compare models, commands and results); **Write a script**. A table of the four ways and when to use each | 45 min |
| 4 · Make it repeatable | The record of a run (`RUN.md`, written by the page, not by the model); a script from the run (`rerun.sh`); test it twice in new folders; the two `.vcf.gz` files differ – find out why (a date in the header) and compare what matters; a README with a statement on the use of AI; download the folder | 25 min |
| Reference | A checklist for believing an agent, the commands, the words, a statement on the use of AI, troubleshooting, the data | – |

There are 47 activities, most of which tick themselves when the student does them (while their chapter is the one shown), and 21 questions (short answers checked automatically, multiple choice, or free text with a model answer). Commands in the instructions have a **show me** button that types them into the terminal; prompts have a button that puts them into the AI's box – the student reads, changes and sends them. Answers are saved in the browser; **My answers** downloads them as an HTML file.

The staff notes (timings, answers, what real models tend to do, keys, troubleshooting, a plan B) are supplied separately. **Do not add the staff notes to this repository** – anything in a public GitHub Pages repository can be read by students.

## Before the session

1. **Keys.** Every student needs an API key for an AI service – one each: an agent uses one request for each step. As a rough guide, allow 50–80 requests per student. With real models, on 6 October 2026, chapters 2 to 4 took 47 requests that were answered – 1 to connect, 4 in the chat, 42 in five runs of the agent – and 10 more that the service turned away (“busy”, “too many requests”); a model that makes more mistakes takes more steps. Decide which of these you use, and tell the students before the session:
   - **A free key for Google's Gemini API**, made by each student at [aistudio.google.com/apikey](https://aistudio.google.com/apikey) (a Google account; 18 or over). The free tier allows each model a few requests per minute and a limited number per day. The limits are counted per project, not per key, so a second key from the same project does not help; Google shows them in [AI Studio](https://aistudio.google.com/rate-limit), and changes them.
     - **What a free key gave on 6 October 2026**, as the service itself reported it: 20 requests a day for each of `gemini-3.8-flash`, `gemini-3.7-flash`, `gemini-3.6-flash` and `gemini-3.5-flash` (for the last also 5 a minute); 15 a minute for `gemini-3.5-flash-lite`, which answered more than 45 requests that day without reaching a limit per day.
     - Around midday the three newest models answered most requests with “busy” (“high demand”, HTTP 503) – and **a request that is answered “busy” counts against the limit per day**: one model was over its 20 for the day after 5 answers and 17 times “busy”.
     - The practical was done from start to finish with that one key all the same, each run of the agent in 12 to 79 seconds: when a model cannot answer, the page asks the next one of `geminiFallbackModels`, and it remembers which ones cannot (see **Services** below). So keep that list long and current, expect the “lite” models to do much of the work – all of it, once the four others have had their 20 requests – and do not plan two sessions on one day with the same free keys.

     **Read Google's [Gemini API Additional Terms](https://ai.google.dev/gemini-api/terms) first.** The version in force when this was written (effective 23 March 2026) says:
     - *“You may use only Paid Services when making API Clients available to users in the European Economic Area, Switzerland, or the United Kingdom.”* Whether a class in which each student uses a free key of their own, in a page that you provide, falls under that sentence is for your institution to decide – ask before you plan on free keys in those countries. (For users there the same terms apply the data rules of the paid service to the free tier as well: what is sent is not used to improve Google's products. Elsewhere Google may use what is sent on the free tier for that, and people may read it.)
     - The API is for use within the [regions that Google lists](https://ai.google.dev/gemini-api/docs/available-regions), by people of 18 or over, “for professional or business purposes, not for consumer use”.
   - **A paid key** – of the Gemini API with billing, or of another service – for each student.
   - **One key of yours for the whole class**, handed out for the session and deleted afterwards, is the least work, but check the terms of the service first: the [Google APIs Terms](https://developers.google.com/terms) ask the holder of a key to keep it confidential. All requests then count against one set of limits and run on your account.
   - **Another service**: the AI tab also takes a key for Anthropic (Claude), and the address, model and key of any OpenAI-compatible service that accepts requests from web pages – for example one that your university provides.
2. **Model names.** Models are retired from time to time. Check that `geminiModel` and the models of `geminiFallbackModels` in `assets/js/config.js` are current ones ([list](https://ai.google.dev/gemini-api/docs/models)). A retired model costs every student one request, which is answered “not found”; after that the page leaves it out.
3. **Network.** The students' browsers must reach the AI service (for Gemini: `generativelanguage.googleapis.com`). Everything else comes from your site.
4. **Rehearse with a real key.** Work through chapters 2 and 3 yourself, on the computers and network the students will use, with a key made the way the students will make theirs. Models change, and what an agent does cannot be fixed in advance – that is the point of the practical, and the reason to try it first. Services change too: in 2026 Google changed the kind of key that AI Studio makes, and old keys without restrictions are no longer accepted; the page sends the key as Google's documentation describes (in the `x-goog-api-key` header). (The page was developed and tested against a stand-in for the AI service that replays prepared replies; see [Tests](#tests). On 6 October 2026 it was also run from start to finish with a free Gemini key – the chat, the four ways of working, the record, the script from a run and its two test runs; what the models did is in the staff notes. That is one afternoon, with the models and the limits of that day. The requests to Anthropic and to an OpenAI-compatible service have only been tested against stand-ins of those services: if you plan to use one of them, try it first.)

## Put it on GitHub Pages

**First put the two parts together.** The practical comes as two zip files: `ai-agents-practical.zip`, the site, and `ai-agents-practical-sources.zip`, the source code of the bundled programs that are under the GNU General Public License (eight archives, 25 MB). Unzip both, and move the eight archives from the folder `sources` into `ai-agents-practical/assets/vendor/licenses/sources/` (a `README.txt` in that folder lists them). The site works without them, but the licence asks whoever publishes those programs to offer their source code with them – see [Credits and licences](#credits-and-licences).

1. On GitHub, create a **new repository** (for example `ai-agents-practical`). It must be public unless your plan supports Pages for private repositories.
2. Upload the site: `index.html` must be at the **top level**, with `assets/` and `data/` beside it.
   - **With [GitHub Desktop](https://desktop.github.com/)** (easiest): *File → Add local repository* (choose the unzipped folder and let it create a repository), *Commit*, then *Publish repository* with “Keep this code private” unticked. GitHub's upload page in the browser is not suitable: it takes at most 100 files at a time, and the site has about 260 (the biggest is 8.8 MB; about 48 MB in all, half of it the source code that the licences of some programs ask you to keep with them).
   - **Or with git:**
     ```bash
     cd ai-agents-practical
     git init && git add . && git commit -m "AI agents for bioinformatics practical"
     git branch -M main
     git remote add origin https://github.com/<you>/ai-agents-practical.git
     git push -u origin main
     ```
3. *Settings → Pages → Build and deployment*: Source **Deploy from a branch**, branch **main**, folder **/ (root)**. Save.
4. After a minute the site is at `https://<you>.github.io/ai-agents-practical/`. Share that address.

The empty file `.nojekyll` stops GitHub from processing the site. The folders `build/` and `test/` are not needed by the site; keep `assets/vendor/licenses/` (see [Credits and licences](#credits-and-licences)).

## The AI: assistant and agent

The **AI** tab asks for a service, a model and a key, tests them, and then shows two parts.

**Chat – the assistant.** A language model that answers questions. Before the first question the page gives it a description of the terminal (the programs and versions, the data files, what is not installed); with each question it sends the name of the student's folder and the names of their files – not the files. Under each block of commands in an answer is a button that puts the commands into the terminal **one at a time**; the student presses Enter and reads the output. A failed command in the terminal offers **Ask the AI assistant about this error**.

**Agent.** The same model in a loop: it writes a command, the page runs it in the student's terminal, what it printed goes back to the model, and so on until the model sends its report. The student chooses how it may work:

| Way of working | What happens |
|---|---|
| Approve each step | Nothing runs until the student allows it. They can change a command first, or refuse it and say why; the model is told. “Run, and stop asking” lets it finish alone |
| Plan first | The model writes a plan and waits. The student approves it or asks for changes; then the model carries it out alone. The plan is saved as `PLAN.md` |
| Autonomous | The model runs commands until it reports. The student watches, and can press **Stop** |
| Write a script | The model writes one script, `analysis.sh`, runs it and repairs it until it works. If it reports without having written the script, the page asks for it once; if there is still none, the run's card says so and offers *Make a script from this run* |

What the page does around the agent – none of it is left to the model:

- Each run gets a **folder of its own**, `~/runs/1-approve`, `~/runs/2-plan` …, with read-only copies of the three input files in `data/` – read-only as a file is on Linux: nothing can be written into them, but a command that puts a new file in the place of one (`sed -i … data/reference.fa`, `gzip data/NA12878_R1.fastq`, `mv -f`) changes the run's copy, and the script made from the run does the same. (The course data itself, `~/data`, cannot be changed; the practical tests a script in a new folder with a fresh copy of it, `cp -rf ~/data ~/check1/` – a copy that can be written into, which the run's inputs could not: a command that failed in the run for that reason, and is in the script because it left something else behind, works there.) Every step starts in that folder (a `cd` lasts until the end of the step). **What a command changes outside the folder is put back** – text files, and also the files that programs wrote (BAM, VCF …), of which the page keeps a copy while the agent works – and the student, the record and the model are told. (`/tmp` is open to the agent as well. A file that the student saves in the editor while a command runs keeps the student's version.) The agent's shell is a new one: it does not see the student's variables, and leaves none behind. It reads commands as a script does, not as a terminal does – the pattern groups `!(…)`, `+(…)` need `shopt -s extglob` first –, because what works in the run has to work in the script made from it.
- A reply of the model is one step: a ` ```bash ` block (its commands run one after the other and stop at the first that fails) and/or a ` ```file:NAME ` block (a file is written; the name must be a plain one in the run's folder). A reply that starts with `REPORT` ends the run. A file may hold code fences of its own – a README with examples of commands – without being cut short, and nothing inside a file block is ever run. Blocks fenced with `~~~` and blocks that are indented are read as well. If a reply ends inside a block that was never closed (the service cut it off), nothing of that block is written or run, and the model is told to send it again.
- **`RUN.md`**, the record of the run, is written by the page from what really happened: the task, the model, the plan and what the student changed, every command with its exit status and the end of what it printed (the last 30 lines, at most 4,000 characters), what was refused or undone, the versions of the programs, and the MD5 checksums of inputs and outputs. `run.json` holds the same for programs. The agent's own report is quoted in it, as a report.
- **Make a script from this run** writes `rerun.sh`: the commands that worked, in order, with the files the agent wrote. Refused commands, and failed ones that left nothing behind, are there as comments.
  - The script is meant to be run in *another* folder than the one the agent worked in. Where a command named the run's folder in full (`/home/student/runs/3-auto/…`, `~/runs/3-auto/…`, `$HOME/runs/3-auto/…`), the script has `"$RUN_FOLDER"` instead, and sets `RUN_FOLDER=$PWD` at its top: the folder it runs in. That holds inside quotes and here-documents as well (inside `"…"` it is `$RUN_FOLDER`; inside `'…'` the quote is closed and opened again around the variable; a here-document that was taken as it is, `<<'EOF'`, becomes one that is expanded, with a backslash before every other `$`, `` ` `` and `\`), and for the **files the agent wrote**: a list of samples, a configuration or a script that names the run's folder is written with `$RUN_FOLDER` in its place, and the script says so above the file. Where the agent changed folder, the script goes back to `"$RUN_FOLDER"` at the end of that step, because the agent's next step started there again. (A run in which none of this happened gets a script without the variable.)
  - **A command that reached outside the run's folder is left out**, as a comment that says why: in a script, run by a person, nothing would put its changes back. Three checks find such commands. *What the page had to undo* after the command. *Which paths the command used when it ran* – the page notes every path the shell worked out for it, and the files that a program was given – so a command is caught that changed nothing outside in the run but would another time (`rm -f` of a file that was not there yet). And *a reading of the command's text*, as the shell reads it: `~/…`, `$HOME/…`, other absolute paths, enough `..` to leave the folder, a `cd` that leaves it – also inside `$( )`, `eval`, `bash -c`, `trap` and texts that are written into scripts; the patterns of awk, sed, grep and jq are left alone, and so are the course data and `/tmp`. The reading also sees the branch that was not taken in the run; where a folder is only known when the command runs (`cd "$OUT" && … ../x`), it leaves the decision to the other two.
  - Left out as well: a command that still names the run's folder where the page cannot put the variable (a `~` inside quotes, a path after another variable); one that runs a script file which reaches outside (or a script whose name is only known when the command runs, if such a file exists); one that the agent ran in a folder outside its own – the course data and `/tmp` excepted; and an `exit` that stands alone, which ended the agent's block of commands but would end the whole script.
  - Three kinds of command stay in the script under a line that begins `# CHECK:`. One that **calls a program this terminal does not have** (`fastqc … || echo "no fastqc"`, `command -v python3 && …`): in the run that program did nothing, and on a computer that has it the command does more than it did here – no check of the page has seen what. One that **uses `~/data`**, the course data of the page, which another computer does not have. And one that runs in a subshell although it had changed the shell (below).
  - The script starts with `set -eu`: it stops at the first command that fails, and at a variable that was never set – the command that set it may be one of those left out, and an empty variable in a path is how scripts delete the wrong folder. It does not use `-o pipefail`: the agent's commands ran without it, and a pipeline that worked in the run must not stop the script.
  - **Where the agent's run went on, the script goes on.** The agent's own commands run without `-e` and `-u`, so a command can end with status 0 in the run and still stop a script that has them: a loop in which `grep -c` counts 0 for one file, a function that returns 1 and is followed by `echo "$?"`, a message that prints a variable nobody set. While a command of the agent runs, the shell notes where `-e` or `-u` would have ended it; the script then has `set +e` (or `set +u`) before that command and `set -e` after it, with a comment that says why. **A command that did not end with status 0 but left something behind is kept**, in the same way: `diff a b > differences.txt` ends with 1 when the files differ, `n=$(grep -c x f)` with 1 when the count is 0 – and the steps after them read that file, or that variable. Only a command that failed *and* changed nothing – no file in the run's folder or in `/tmp`, no variable, function or option of the shell – is left out as a comment. So is one that failed **because this terminal lacks something** – `python3 … > answer.txt`, a plugin of bcftools –, whatever it left behind (an empty file, as a rule): on a computer that has the program the command works, and does more than it did in the run. A line that asks how the command before it ended (`$?`, `PIPESTATUS`) stays straight behind that command: the `set -e` of the page comes after it. If the run set a trap for `EXIT`, the script takes it away at its end (`trap - EXIT`, with a comment): the agent's shell does not end the way a script ends, so that trap never ran in the run.
  - **Where a command ended as a script ends, it ends alone.** `exit` inside a command, the agent's own `set -e` or `set -u` (models like to begin a block with `set -euo pipefail`), `${NAME:?message}`, `exec`: in a script each of these ends the script. In the agent's run it ended the command, and the run went on with its next step – with the files the command had written by then. The script lets such a command run in a subshell, `( … )`, with the options the run had at that point: it ends there as it did in the run, and the script goes on. What the command had changed *in the shell* before it ended – a variable, a function, an option – stays in the subshell; the script names it under `# CHECK:`, and a later command that needs it stops the script (“unbound variable”). A line of simple commands that failed under the agent's `set -e` (`diff a b > d.txt`) was not cut short: `set +e` around it is enough.
  - No check can see everything a program does with a path that is put together while it runs, so the script's header and the instructions tell students to read the script before they run it.
- Limits: at most 20 steps for a task (`agentMaxSteps`); of long output the model gets the beginning and the end (3,000 characters, `agentOutputChars`). A command that has not ended after 150 seconds is stopped by force (`agentCommandSeconds`): the programs are started afresh. What programs wrote during that command is gone – the run's card, the record and the model are told which files – and their earlier files come back from the browser's storage as they were before it (text that the command itself had written in the place of such a file stays).
- A run that is under way when the page is closed or loaded again cannot go on, and has no record (the record is written when a run ends). Its folder gets a note that says so, and the run is listed as interrupted.
- When no model can answer and waiting can help – every model is over its limit per minute, or busy, or the connection gave no answer – the agent waits, with a countdown (as long as the service asks, between 5 and 90 seconds; 20 seconds when the models are busy), and asks again, up to three times for one reply. If there is still no answer, the run ends with a message that says what each model said. It ends at once when waiting cannot help: every model over its limit for today, or a key that is not accepted. The run's folder and its record stay, and the task has to be given again.
- A reply with nothing in it is asked for again, up to three times; a reply that is neither a step nor a report is answered with a reminder of the format, twice at most. A reply that Gemini cuts off as a “malformed function call” gets its commands back: the service sometimes takes the ```` ```bash ```` block of a model for the call of a tool, ends the reply there and reports what it took away (seen with `gemini-3.5-flash`, three times in about eighty replies) – the page puts the block back, so the step is not lost.
- **The report is the reply without a command.** A reply that holds a command or a file is a step, whatever else it says. A model that writes REPORT after the block of its command – before the command has run – has written down what it expects, not what it saw (a real model did this, with numbers that the command then did not print). The page runs the step, keeps that early text out of the report, says so on the run's card, shows it in the record under the step – after the real output – and tells the model to send its report again when it has seen the result. And a line that only begins with the name of a file (“REPORT.md is not there yet”) does not end a run.
- While the agent works the terminal is locked for typing; the student can watch it there. While one of its commands is running, what the student does to files elsewhere on the page (a new file or folder in the Files tab, a file made by a button of the instructions) waits until that command has finished; saving in the editor does not wait. `open`, `nano` and `download` do nothing for the agent, and its commands are not added to the student's command history (the ↑ key).

**Services.** Google Gemini (first, because of its free tier), Anthropic (Claude) and any OpenAI-compatible service (an address and a model name; the service must allow requests from web pages). Every answer shows which model replied, and `RUN.md` names the models of a run.

**When a Gemini model cannot answer**, the page asks the next model of `geminiFallbackModels`, and remembers what the first one said, so that it is not asked again before that can have changed:

| The model … | The page … |
|---|---|
| is busy (“high demand”, HTTP 500–504) | asks the next model, and leaves this one alone for 2 minutes – for 4, 8, at most 15 if it is busy again when its rest is over |
| is over its limit per minute (429) | asks the next model, and comes back when the service says the limit is over (usually within a minute) |
| is over its limit per day (429, and the service names the limit) | asks the next model, and does not ask this one again before the time the service gives (midnight UTC, on 6 October 2026) |
| is not found (404: retired, or a wrong name) | asks the next model, and never this one |
| gives no answer: the connection fails, or nothing comes for `aiWaitSeconds` (60) | asks the next model, and leaves this one alone for a minute. Two models in a row without an answer: the page stops, and says that the connection may be down – unless another model answered a moment before |
| breaks off in the middle of an answer | takes back what had arrived, and asks the next model |

When no model is left that is not at rest, the two that have rested longest of the busy or silent ones are asked again. The memory belongs to the key and is gone when the page is loaded again. While the chosen model is at rest the bar of the AI tab says so (“busy”, “over its limit”) and shows an amber dot; the answers then come from another model, and each says from which. An error of another kind – a key that is not accepted, a request that the service refuses – is shown at once. For the other services there is one model: if it is busy, the page tries once more.

**The key** is kept only in that browser tab (`sessionStorage`) and sent only to the chosen service. It is never written to the site, to the student's files, to a record or to their work file. **⚙ → Disconnect** in the AI tab and **Start again** remove it; a browser that restores closed tabs can bring it back with the tab, so on shared computers students should disconnect before they leave. (Unticking “Keep the key in this browser tab when the page is loaded again” keeps it in memory only.) **Never put an API key in `config.js`** or anywhere else in the site: anyone can read a public site's files.

**Written for the practical, in JavaScript:** the shell; the commands that work on the page's folders rather than on the bytes of files – `ls cd pwd pushd popd dirs mkdir cp mv rm rmdir touch find xargs du stat tree file chmod basename dirname realpath readlink mktemp column tac rev nl sleep env printenv timeout`; small programs that scripts call in passing – `getopt` (the one of util-linux, which reads long options: `getopt -o hi:o: --long help,input:,output: -- "$@"`), `stdbuf`, `tty`, `locale`, `logname`, `groups`, `sync`; the small tools that there is no WebAssembly build of – `sha1sum sha256sum sha384sum sha512sum od hexdump xxd base64 split truncate expand unexpand expr` and `bc` (a calculator in bc's language: `scale`, variables, functions, `-l`, `ibase` and `obase`); three commands of the page itself – `open FILE` and `nano FILE` (show or edit a file in the Files tab) and `download FILE` (save a copy on the student's computer; a folder as a .zip); and the shell's own commands (`echo printf test read getopts export declare …`). They take the options that scripts and AI models use, and print what the GNU programs print: `ls` in GNU's layouts (`-l` with its column widths and `total`, `-h`, `-s`, `-C`, `-x`, `-m`, `-R`, the sort orders, `--hide`, `-I`), `find` with `-exec … +`, `-execdir`, `-printf`, `-newer`, `-delete`, `-print0`, `stat -c`, `du -h`, `cp -p`/`-u`/`--parents`, `rm -i`, `od -c`, `split -l`/`-b`/`-n`, `base64 -d`, `xargs -0 -I{}`, the checksum programs with `-c` … `file` judges a file by what is in it, as on Linux (`Blocked GNU Zip Format (BGZF; gzip compatible)` for a BAM file, `ASCII text` for a FASTQ file). The commands and tools – not the shell's own commands – do not have every option of the GNU programs: `NAME --help` (or `man NAME`) lists the options that each one has here, and as a rule an option that is not there is refused with a message, not passed over in silence. (The AI is told the same, so that an agent can look an option up before it uses it.) At this terminal `ls` prints one name per line, as it does into a pipe or a file, and without colours.

The **shell** is a subset of bash: pipes, lists (`&& || ;`), redirection (`> >> < 2> 2>&1 &> >&2`, here-documents and here-strings; `> /dev/stderr`; the descriptors 3 to 9 – `exec 3< FILE`, `read -u 3`, `>&3`, `exec 3>&1 … exec 1>&3 3>&-`), process substitution (`diff <(sort a) <(sort b)`, `while read x; do …; done < <(command)`), quoting (also `$'…'`), variables and arrays (also associative), name references (`declare -n`), parameter expansion (`${x:-y}`, `${x%.*}`, `${x/a/b}`, `${x:2:5}`, `"${@:2}"`, `${!name}`, `${x@Q}` …), `$( )`, `$(( ))`, globs (`*`, `?`, `[[:digit:]]`; `**` with `shopt -s globstar`; the groups `+( )`, `@( )`, `!( )` – at the prompt, and in a script after `shopt -s extglob`, as in bash) and brace expansion, word splitting by `IFS`, `if` / `for` / `while` / `until` / `case`, `[ ]` and `[[ ]]` (with `=~` and bash's regular expressions: `\.fastq$`, `[[:digit:]]+`, `BASH_REMATCH`), `(( ))`, functions (`declare -f` and `type` print them as bash does), `local`, `declare`, `getopts`, `read` (`-r -a -n -N -d -u`), `mapfile`, `printf` (as bash's own: `%q`, `%b`, `%(%F)T`, `-v`), `${PIPESTATUS[@]}`, `$_`, `$LINENO`, `BASH_VERSINFO`, `set -euo pipefail` (with bash's rules for where a command that fails does not end the script: in the test of an `if` or a `while`, left of `&&` and `||`, after `!` – and in a function, a block or a subshell that stands there), the other options of `set` and `shopt` that change what a script does (`-x -v -n -a -f -C -E`; `extglob nullglob failglob globstar dotglob nocaseglob nocasematch lastpipe inherit_errexit`; an option that bash does not have is refused), `trap … EXIT` and `ERR` (with `$?`, `$LINENO` and `$BASH_COMMAND`; `exit` in a trap sets the status), `exec > >(tee FILE) 2>&1`, `umask`, `timeout`, `caller`, `compgen`, `hash`, `time` (with `TIMEFORMAT` and `-p`), `bash script.sh` and `./script.sh`, `bash -c`, `bash -n`, `bash -x` and bash's other option letters (one that bash does not have is refused), `export -f`, `env NAME=value command`, `TZ=Europe/Paris date`. Nine things that matter when a script written here is run on another computer are as in bash:

- **The programs get the exported variables, too.** `export MIN_DEPTH=20` (or `MIN_DEPTH=20 awk …`, `env MIN_DEPTH=20 …`) is in awk's `ENVIRON`, in jq's `env` and in `getenv()` of every program; a variable that was not exported is not. `export LC_ALL=C` makes `sort`, `grep`, `sed`, `wc` and `awk` work on bytes, as on Linux.
- **`~` is the home folder only where the shell puts it there:** at the start of a word that is not in quotes (and after `=` or `:` in `NAME=value`). In quotes it is a character – `OUT="~/results"; mkdir -p "$OUT"` makes a folder called `~` in the folder one is in, and `samtools view "~/x.bam"` finds nothing – here as on Linux.
- **A file that is started is run by the program that its first line names.** `./count.awk` with `#!/usr/bin/awk -f` is run by awk, a file with `#!/usr/bin/env bash` (or without such a line) by the shell; a program that is not here (`#!/usr/bin/env python3`) gives the message and the status of Linux. All that follows the program on that line is handed over as one word, as on Linux: `#!/bin/bash -eu` works, `#!/bin/bash -euo pipefail` and `#!/bin/bash -e -u` fail there – and here, where the terminal also says what to write instead.
- **An empty name is no file, and a carriage return is no blank.** With `OUT` not set, `[ -d "$OUT" ]` is false, and `mv results.txt "$OUT"` fails and moves nothing. A script with the line ends of Windows fails as it does on Linux, where the carriage return is a character of the last word of each line (`$'\r': command not found`); the terminal says where such messages come from and how to take the characters away (`sed -i 's/\r$//' FILE`).
- **A path is read name by name.** `results.txt/` names a folder or nothing: `rm -f results.txt/` removes no file, and `cat results.txt/` says “Not a directory”; `nosuch/../data` is not there, because `nosuch` is not. The folder one is in is not moved by `mv . ../new` (“Device or resource busy”), but it can be removed – `rm -rf "$PWD"`, the tidying up at the end of many scripts –, and what is written there afterwards fails, as on Linux.
- **A script that is started gets only the exported variables.** `REF=ref.fa; bash step2.sh` – in `step2.sh` there is no `REF`, and no function of the caller, unless it was exported (`export REF`, `set -a`, `export -f name`, `REF=ref.fa bash step2.sh`). Subshells `( )` and `$( )` see everything, as in bash.
- **A program reads the input of the block it stands in.** In `{ head -n 1; sort; } < FILE`, in a function used as a filter (`cut -f 1 FILE | count`) and in `bash script.sh < FILE`, the programs read that input, each from where the one before stopped; a program that does not read leaves it alone (`while read s; do samtools flagstat "$s.bam"; done < samples.txt`). What a program writes goes through blocks, functions, loops and `bash -c` byte for byte (`f() { samtools view -b "$1"; }; f x.bam > y.bam`).
- **The files after `>` are opened before the command runs, and filled as the commands print.** `ls > list.txt` lists `list.txt`, and `sort f > f` leaves an empty file – the terminal says why. A command whose file cannot be opened fails alone: in `sort < nosuch.txt | wc -l` the second command still runs and prints 0, and the status of the pipeline is that of `wc` – `set -e` does not end the script there, `set -o pipefail` makes the pipeline count as failed. What a block, a loop or a function prints into a file is there when its next command looks: `{ echo start; wc -l < out.log; } > out.log` counts one line, `for s in A B; do [ -s table.tsv ] || echo header; echo "$s"; done > table.tsv` writes the header once, and what a function adds to a log with `>>` comes after what the block around it printed before.
- **Mistakes are the same mistakes.** The shell counts in whole numbers of 64 bits: `$((7 / 2))` is 3, and `$((1.5 * 2))` or `$((08 + 1))` is an error, not a wrong number (for decimals there are `bc` and `awk`). In a script a failed command is reported with the name of the script and the line – `analysis.sh: line 12: bwa: command not found`. An unset variable under `set -u` ends the script; a mistake in an expansion (`${x!}`, a division by 0) ends the line it stands in, and the script goes on with the next line – with status 1, so that `set -e` ends it where bash would.

899 scripts are compared with real bash 5.2 in the tests (`test/t_lang.py`): same output, same exit status; and `test/t_files.py` runs random sequences of file commands in the page and in bash and compares every file afterwards. For this version about 9,200 further command lines – most of them written by eight independent reviewers who were looking for differences, the rest while mending what they found – and 2,050 random sequences of file commands were compared in the same way with bash and the GNU programs; what still differs is listed here. (Random sequences went on finding things to the end: of the 450 that were added last, two differed – the permissions of the backup that `sed -i.bak` makes, and the status of `gunzip` for an empty file whose result is there already. Both were mended, and the 900 sequences run after that were the same. A seed that nobody has tried may find another.) **Different from bash:** the commands of a pipeline run one after the other, each one's output being the next one's input – the result is the same, but a command that never ends (`yes`, `cat /dev/urandom`) must not feed a pipe, and a pipeline that reads a file while another of its commands writes to it (`sort f | tee f`) reads the file whole, a file that is written before a reader which stops early is written whole (`cat big.sam | tee copy.sam | head`: on Linux `copy.sam` is cut short), a command that reads only part of what is piped in leaves another amount for the next one (`seq 5000 | { head -n 2; wc -l; }`), and `shuf -n` with `--random-source` picks other lines from a pipe than it does on Linux (from a file: the same); the commands in `<( )` run before the command they belong to; `awk` cannot start other programs (`system()`, `print | "sort"`); text is UTF-8 – a file in another encoding (Latin-1, say) goes through the programs byte for byte, but the shell's variables and the terminal's own text commands (`read`, `$( )`, `tac`, `rev`, `nl`, `xargs` …) turn the bytes that are no UTF-8 into the replacement character; of `/dev` there are `null`, `zero`, `random`, `urandom`, `stdin`, `stdout`, `stderr` and `tty` (what is written to `/dev/tty` goes where the messages go); opening one file for reading and writing (`<>`) and redirecting the terminal's own input and output with `exec` at the prompt (in a script it works) are refused with a message; a command that asks – `rm -i`, `cp -i`, `mv -i`, `find -ok` – takes the answer from its input (`echo y | rm -i x`), and typed at the terminal, where nobody can answer while a command runs, the question counts as “no” and the terminal says so; `timeout` stops at once what the page carries out itself (`sleep`, a loop, a script), but a program that is running runs to its end – the status is then 124 all the same, with a note; a command whose reader stops early (`samtools view x.bam | head`) ends with status 141, as on Linux, when it had more than 64 KiB left to write – with less, real bash reports 141 on some runs and 0 on others (the timing decides), the page always 0, and under `set -o pipefail` it adds a note that the same pipeline can stop a script on Linux; `trap` is carried out for `EXIT` and `ERR` – a trap for a signal is kept and listed, but no signal ever arrives; a syntax error inside `$( )` is reported when the line is carried out, not when it is read; `sleep` ends after 10 seconds; the times of files have a resolution of one millisecond; with `LC_ALL=C` the programs work on bytes, but the shell itself and the terminal's own commands still count characters (`${#x}`, `printf '%5s'`, `rev`); of the environment, `TMPDIR` reaches a program only if it names a folder inside the home folder (a program's own `/tmp` is not the `/tmp` of the terminal); a terminal whose folder was removed goes to the nearest folder that is still there when the typed line has ended, and says so (in a script the shell stays where it was, as bash does). **Not there:** background jobs (`&`), a network, `sudo`, installing anything, links (`ln`), named pipes (`mkfifo`), `tar`, a file descriptor that bash numbers itself (`exec {fd}> FILE` – the descriptors 3 to 9 are there); each tells the user (or the agent) so. Every program runs on one thread; thread options are accepted or taken out with a note. The clock is that of the computer; `date -u`, `TZ=UTC` and any zone that the browser knows by name (`TZ=America/New_York date`) work, for `date`, `ls -l`, `stat`, `touch -d`, `find -newermt`, the file times that `diff -u` prints, awk's `strftime` and `printf '%(…)T'`.

**Small differences that were looked at and left** – none of them was met in a script of the kind this practical is about. A script of one's own that stands earlier in `PATH` than `/usr/bin` does not take the place of a program of the same name. `sh` is this shell too (where `sh` is dash, some messages differ). In a file that is read with `source`, `caller` and `FUNCNAME` name the file where bash names the function that read it. `mapfile -C` does not call its command, and `shopt -s xpg_echo` changes nothing. `set -x` prints `export NAME=value` in one line where bash prints two, and `declare -p` writes a value with a newline in double quotes where bash writes `$'…'`. A time zone in the POSIX form with an offset (`TZ=UTC-2`, `TZ=CET-1CEST`) is not understood – names such as `Europe/Paris` are –, and the terminal says so. The file commands of the page show a name with a control character in it as it is, where the GNU programs write `'out'$'\r'`. For the empty name, `mv` and `cp` use the words of coreutils 8.32 (`cannot move 'x' to ''`), and `cp -r FOLDER ""` is an error (coreutils 9.4 copies what is in the folder into the folder one is in). Upper-casing ß in `sed` and `awk` gives ẞ (the C library of the WebAssembly programs; the shell's `${x^^}` leaves the letter, as bash does). Of Bowtie 2 the aligner itself is run, not the perl script around it; what that script does before and after the aligner – it looks for the index, and reports a failure – the terminal does in its place, in the script's words and with its statuses. `bowtie2-inspect` is not there, and `bowtie2-build` prints other progress messages (it sorts in smaller blocks; the index is the same, byte for byte). `gzip` and `gunzip` follow gzip's rules for names and statuses, but bgzip does the work: `-l` and `-S` are not there, `-v` prints nothing, and a file that is no gzip file is refused in bgzip's words (by `gunzip FILE` in gzip's own, before it asks whether the result is there already; an empty file ends gzip there, as on Linux). A program that reads the file its own output goes to finds it empty: `wc -c a b > b` counts 0 for `b` (GNU wc counts what it has itself written by then), and `grep x f > f` ends with status 1 (GNU grep refuses such a file with 2) – the contents are lost either way, and the terminal says why. A folder as the input of a command (`sort < results/`) is refused by the shell with status 1; on Linux the program fails, each with a status of its own. In a pipeline in which one command's file cannot be opened, the command before it has the status 141 if it is a program that wrote something, else 0 (in bash: 141 or 0, as the timing has it). After `cp -r FOLDER FOLDER/sub` (refused by both) GNU cp leaves a part of the copy behind, the page nothing. Of bash's own options, `+B` does not switch brace expansion off, `-o` without a name lists nothing, and `$-` never shows `P`, `k` or `b`; `BASH_EXECUTION_STRING` is empty; `hash -t NAME` names a program that has not been used yet, and `hash -p` does nothing; a first line `#!/bin/bash -s` runs the file. After the folder above the one the shell is in was moved, `pwd` gives the new name at once (bash: after the next `cd`). `${a[*]@A}` writes single quotes where bash writes double quotes. In what a program says about `<( )` the name is `/tmp/.psub-N`, not `/dev/fd/N`. With a seed other than 0, `samtools view -s SEED.FRACTION` keeps other reads than samtools on Linux does – about as many, not the same ones: samtools feeds the seed through the C library's random numbers, and the library of the WebAssembly programs is not the one of Linux. The terminal says so each time; with seed 0 (`-s 0.25`), and with `seqtk sample -s`, the reads are the same everywhere. `sort -R --random-source=FILE` gives another order under `C.UTF-8` (with `LC_ALL=C`: the same). `samtools reheader -c COMMAND` is refused – a program cannot start a program here – with the way round it. The permissions of a *folder* are shown (`ls -l`, `stat`) but not enforced: in a folder without write permission (`chmod a-w results`) the page still makes, renames and removes files where Linux says “Permission denied” – read-only *files* are treated as on Linux. `[ -t 2 ]` is always true, and the tests on `/dev/stderr` see a terminal, also when the messages go to a file or a pipe (`[ -t 0 ]`, `[ -t 1 ]` and the tests on `/dev/stdin` and `/dev/stdout` follow the redirections); there is no `/proc` – the tests answer for `/proc/self/fd/0`, but nothing can be read from it. When the folder a script is in is removed and made again under the same name without a `cd` (`rm -rf "$PWD"; mkdir -p "$PWD"`), the page carries on in the new folder, where bash fails until the next `cd`. A file that is renamed or replaced while a block or `exec > FILE` is still writing to it does not take the later output with it. A block that writes a file with `>` while its own commands add to the same file with `>>` gets the lines in the order they were written (in bash the two writers overwrite each other); the same holds when the output and the messages of one command are sent to one file by two redirections, `cmd > F 2> F` – write `cmd > F 2>&1`. `mv -b` is not there, and a name longer than 255 bytes is accepted. Of what one command prints, the terminal shows the first 2,000 and the last 1,000 lines, and says how many lie between. `bc` has no Bessel function (`j(n,x)`), and parentheses nested more than about a thousand deep are too much for it; it takes `define f(x) { return x*x }` – no `;` before the `}` –, which GNU bc refuses, and the `adr=` in its runtime errors is always 0. What samtools, bcftools and bgzip print that is no text – a BAM, the bytes of `gzip -c` – is not shown in the terminal and not taken by `$( )`; the terminal says how many bytes there were, and into a file or a pipe they go byte for byte. samtools, bcftools, bgzip, tabix, seqtk and the Bowtie 2 aligner report an option they do not know in the words of another C library (`sort: unrecognized option: nosuch`, where Linux has `sort: unrecognized option '--nosuch'`); the GNU programs use the same words everywhere. A few of Bowtie 2's messages for a wrong command line are the aligner's where Linux shows those of the wrapper script (`-1` without `-2`), and its line `Command:` names the aligner without a folder. Where a program fails part-way, what it had written by then can end at another place: `bowtie2 -U reads.fq,nosuch.fq -S out.sam` gives the same messages and the same status as on Linux, and a SAM file that ends at another read. `find`, `ls -U` and `ls -f` list a folder in the order of the names; on Linux that order is the file system's own, which is none (sort what `find` prints). A program that is given `/dev/fd/0` as a file calls it `/dev/stdin` in what it prints, and `xargs` does not warn when `-n` and `-I` are given together.

Programs that are not installed (`bwa`, `gatk`, `fastqc`, `python`, `conda`, `wget` …) give “command not found” and a hint at what is there instead. That is deliberate material: the assistant knows what is installed only because the page tells it.

A program sees the page's folders under other names than the student does, so the page rewrites the paths among a program's arguments – and leaves alone what is no path although it begins with a slash: the patterns and programs of awk, sed, grep and jq, the delimiter of `cut -d /`, the characters of `tr / _`. The variables of the environment are handed over as they are.

Each run of a program starts afresh, as a process does on Linux: nothing is carried from one run to the next. (Left running, a WebAssembly program keeps its C globals: minimap2 wrote the read group of an earlier `-R` into every later alignment.) It costs a few hundredths of a second per run and needs no network: a program is fetched once, when it is first used, and the page then keeps it in memory. (After a forced stop the programs start anew and are fetched again – as a rule from the browser's cache.)

The three input files in `~/data` are **read-only** for every program and for the agent: a change is refused or put back, with a message. Any other read-only file – `chmod a-w FILE`, a copy of such a file, the inputs in the folder of an agent's run – is treated as Linux treats it for a normal user: nothing can be written into it (`>>`, `>`, `tee`, `sort -o`: “Permission denied”), but in a folder that one may write to, a command can put a new file in its place or remove it (`sed -i` and `gzip`, which give the new file the old one's permissions; `mv -f` onto it; `rm -f`). `chmod u+w FILE` makes it writable. (A copy made straight from the course data – `cp ~/data/reference.fa .` – is an ordinary, writable file of the student's; on Linux the copy of a read-only file is read-only.) A program that does not end can be stopped: Ctrl+C once lets the running program finish and skips the rest; a second Ctrl+C stops it by force. The programs are then started again, and the files that programs had written – which live in the programs' memory – come back from the browser's storage. A file that was written in the last seconds before the stop comes back as its earlier version, or not at all; the terminal names such files.

What was changed in the programs and their runtime to make them behave in a browser as on Linux is listed in [`assets/vendor/biowasm/RUNTIME-PATCHES.txt`](assets/vendor/biowasm/RUNTIME-PATCHES.txt).

## What students keep

- **In the browser**, per browser and computer: ticks and answers, the files they and the agent wrote, the records of the runs and the AI settings (`localStorage`); what programs wrote – BAM files, compressed VCF, reports – (`IndexedDB`). All of it is there again after a reload, with one exception: a file that a program wrote in the last two or three seconds before the page was closed (or one larger than 40 MB) has not reached the storage. Such a file never comes back as an older version – it is gone, and the terminal names it after the reload. (For a file larger than 40 MB the page says so when the file is made.) The key is kept for the tab only (see above).
- **One tab.** Two tabs of the same browser would save to the same place and write over each other's work; the page says so in both when it is open twice. (Neither tab deletes the program output that the other has stored.)
- **A full storage.** Browsers give a site about 5 MB for `localStorage`, shared by all pages of the site – so by every practical you host under the same address (`name.github.io/…`) that a student has done in the same browser. When it is full the page says so, in a note and in the terminal: from then on the state of the files is kept for the open tab only – it is there after a reload, but not after the tab was closed (what programs wrote still is). **Save all my work to a file** saves everything as it is in the page. **Start again** in a practical that is finished frees its part.
- **My answers → Download my answers** saves the answers as an HTML file (to hand in, or to open in Word).
- **My answers → Save all my work to a file** saves ticks, answers, text files, records and settings in one small `.json` file; **Open my work from a file** restores it in any browser. The large files that programs wrote are not in it: a script makes them again – which is the lesson of chapter 4. The key is never in it.
- **Chapter 4** ends with a download of the tested folder as a zip: data, script, record, results, README.
- **My answers → Start again** deletes everything the page has saved in that browser, including the key. On shared computers, ask students to do this at the end – or at least **⚙ → Disconnect** in the AI tab. Closing the browser is not enough where browsers restore their tabs.

## Editing the content

The instructions are written in `build/chapters.py` – one Python function per chapter, with small helpers from `build/lib.py` for activities, questions, command and prompt buttons – and put into the page shell `build/template.html` by:

```bash
cd build
python3 make_page.py      # writes ../index.html; reports the number of tasks and questions, and any name used twice
```

You can also edit `index.html` directly, between `<!--CHAPTERS-->` and `<!--/CHAPTERS-->`; then leave `build/` alone, because the next `make_page.py` would overwrite your changes.

- **Activities:** `task("id", "text", auto="EVENT key=value", check="name:arg")`. `auto` ticks the activity when something happens – for example `term:command name=fastp code=0` (a fastp command that succeeded, typed by the student), `term:command line~11616` (the line contains this), `term:command line~md5sum line~bcftools` (several conditions: all must hold), `ai:ask text~bwa`, `ai:answer tab=chat`, `agent:start mode=plan`, `agent:approve choice=edited`, `editor:open path~-plan/RUN.md`, `script:done code=0 path~/check1/`, `file:create name=README.md`, `project:download root~/check1`; alternatives are joined with `||`. A `term:command` carries `line`, `name`, `sub`, `code` and `cwd` (the folder the terminal is in afterwards, as in the prompt: `cwd~/runs/`). `check` looks at the state whenever something happens (but not while a command of the agent is under way): `exists:check2/variants.vcf.gz`, `has:FILE|REGEX`, `connected`, `runs:auto:2` (two finished autonomous runs). An activity ticks only while its chapter is the one shown. What the **agent** does in the terminal – its commands, the programs and scripts they run, the files they make – never ticks a student's activity.
- **Questions:** `q("id", "question", "model answer", accept=REGEX, hint=…)` – with `accept`, a short answer is checked; `mcq("id", "question", [(option, correct, why), …])`.
- **Buttons:** `cmd("ls -l data")` shows a command with a *show me* button; `prompt(text, tab="agent", mode="plan")` shows a prompt with a button that puts it into the AI's box.

The numbers quoted in the instructions come from the programs as they run in the page. If you change the data, a program or a version, check them again (next section).

## Checking the numbers

Every number in the instructions and model answers was produced by the programs in the page (`test/t_facts.py` prints them all), and compared with **native Linux builds of the same versions** (minimap2 2.22, samtools 1.17, bcftools 1.10, fastp 0.20.1, Bowtie 2 2.4.2) – the builds of Bioconda: samtools 1.17 linked with HTSlib 1.21 (the first line of what `samtools stats` writes names it, and is the only line of it that differs), bcftools 1.10 with HTSlib 1.10, whose bgzip and tabix were used. The versions matter in the comparison too: bcftools 1.10.2 with a newer HTSlib gives QUAL 222, not 178, at position 11,616 on the same Bowtie 2 alignments.

| | In the page | Native |
|---|---|---|
| Read pairs; read length | 3,519; 76 | – |
| fastp: reads passing the filter | 6,170 of 7,038 (864 low quality, 4 too many N); adapters trimmed in 42 reads | the same; with one thread (`-w 1`) the files of filtered reads are identical, byte for byte (with more threads native fastp writes the same reads in another order) |

With seed 0 – `-s 0.25` – both keep the same 1,746. The terminal prints a note whenever a seed other than 0 is used |
| minimap2 `-ax sr`: mapped; properly paired | 6,817 (96.86 %); 94.77 % | the same; the alignments are identical, byte for byte |

Two variant lines therefore differ in their numbers (QUAL 74 natively against 71 at `human_CYP2C9:3047`; DP 74 against 73 at `human_CYP2C19:5124`), and so does the checksum of the variant lines (`77e6ea46…` in the page, `c5f821a1…` natively) |

Three results differ between the page's programs and native ones of the same versions, and all three are in the table: the places Bowtie 2 gives to 21 read pairs, fastp's estimate of the duplication rate, and which reads `samtools view -s` keeps for a seed other than 0. None comes from a version: the page's programs are 32-bit builds with another C library. For this version 84 whole analyses of the kind a language model writes (15 to 50 lines each: quality control, mapping with both mappers, calling, filtering, coverage, reports, housekeeping) were run in the page and with the native programs, each twice in the same folder, and compared line by line and file by file. 61 printed the same and left the same files, both times (58 in an earlier run: for three analyses real bash gives another result when its second run falls into the same second as its first, because bcftools, tabix and samtools go by the time of an index, to the second, to tell whether it is stale). In the other 23, what differed was one of those three results; something that the page does not have or does in its own way, as listed under [The terminal and its programs](#the-terminal-and-its-programs) (a plugin of bcftools, `bowtie2 --un`, `samtools reheader -c`, `sdiff`, `kill`, python, `/dev/full`, the order of an unsorted `find`, the wording of a message); something that differs by its nature (the bytes of a compressed file, a time, a date or the full path of the folder written into a file); or the comparison itself, not the page: the native runs were made as root, which may write into a read-only file, is asked nothing by `mv` and takes no `PS4` from the environment; the native samtools had a newer HTSlib, the native tabix an older one; and one script lists a folder into a file in that folder, which is a race on Linux. (The bytes of a compressed file – BAM, CRAM, BCF, `.gz` – are not, as a rule, those that a native program writes: the compression library is another one, and `gzip` is bgzip here. What is in the file is the same; compare such files by what they hold, as chapter 4 does with the variants.)

The same was done with 79 runs of the agent – 52 of them written to break the script that the page makes from a run –: each was turned into `rerun.sh` and run by real bash with the native programs. 64 of the 79 scripts left exactly the files of their run. In two more the script itself is a race on Linux (a list of a folder that is written into that folder; a file that `tee >( )` writes, read at once). In six the files differ where they must: they name the folder they were made in (2), carry temporary names made at random (1), come from Bowtie 2 (2), or were made by commands that reached outside the run's folder and are therefore left out (1). In four, a command that failed here for want of a program is left out, and the empty file it had left is not there. Two scripts stop – at a command above which the script says why (a path with `~` inside quotes; a `source` that `set -e` cut short after it had set variables) –, and for one run the page makes no script, because its only commands were a syntax error.

The checksums of the data are in `data/MD5SUMS` and in the README template of chapter 4.

## Data

`data/NA12878_R1.fastq` and `data/NA12878_R2.fastq` are 3,519 pairs of real 76-base Illumina exome reads of the public reference sample **NA12878** (run SRR098401, 1000 Genomes Project) from around the genes *CYP2C19* and *CYP2C9*; `data/reference.fa` holds two pieces of the human reference genome hg19, `human_CYP2C19` (chr10:96,530,001–96,560,000) and `human_CYP2C9` (chr10:96,699,001–96,725,000). The variant *CYP2C19\*2* (rs4244285) is at position 11,616 of `human_CYP2C19`. Nothing is simulated. How the files were made, with addresses, checksums and limitations, is in [`data/provenance.json`](data/provenance.json) and [`data/README.md`](data/README.md).

The two genes are close relatives: for about two thirds of the reads Bowtie 2 finds a second place that fits, and for about one in twenty a place that fits equally well. So the two mappers do not place every read alike, and the lists of variants differ (60 and 50) – useful when students compare runs.

## Privacy

- The site itself collects nothing and has no server side: no accounts, no analytics, no cookies. Work is saved only in the student's browser.
- **What goes to the AI service** (and only there, from the student's browser, with the student's key): what the student types in the AI tab; the page's description of the terminal; the names of the student's files; for a failed command, the command and its output; and for the agent, its commands and what they print – which can include lines of the data files. The files themselves are not uploaded. The AI tab says this before a key is entered.
- The data are from a public reference sample. **Students must never paste personal or patient data into the AI tab**, and the instructions say so. Users of the Gemini API must be 18 or over. On its free tier Google may use what is sent to improve its products, and people may read it – except, by Google's terms, for users in the European Economic Area, Switzerland and the United Kingdom, for whom the data rules of the paid service apply ([terms](https://ai.google.dev/gemini-api/terms)). The AI tab tells students so before they enter a key.
- With a key of yours that you hand out, the requests of all students run on your account.

## Browser support and limits

- A current browser on a laptop or desktop. The page was developed and tested with Chromium (the engine of Chrome and Edge); it uses standard features that current Firefox and Safari also have, but it was not tested with them – try them before a session if your students use them. The page works down to phone width (the workbench then slides over the instructions), but a keyboard is needed in practice.
- The programs need WebAssembly (with SIMD, for Bowtie 2) and Web Workers – all current browsers have them. Everything runs on one thread; with this data each program takes a few seconds at most.
- Browser storage: text files up to 300 kB each (3.5 MB in all) and program output up to 40 MB per file are kept. Private windows and locked-down lab computers may clear storage when the browser closes: use **Save all my work**.
- The shell is a subset of bash (see above); the agent's task, steps and output are limited as described.
- An AI service can be slow, busy or over its limit; the page waits, tries other models and says what happened, but it cannot make a service answer – a run of the agent can end with an error of the service, and is then started again. With a free key the models that answer change from one request to the next, so the runs of one student need not come from one model. There is no offline mode for the AI – by design.
